# 개인 노트북으로 뉴스 워크플로우 이전

작성일: 2026-09-14. 현재 코드의 읽기 전용 점검을 바탕으로 작성한 이전 계획. 실제 자료 복사·인증정보 열람·새 기기 연결·회사 자동화 중단은 아직 수행하지 않음.

사용자 확인 반영: 이전 대상은 **Windows PC**, **24시간 켜둘 예정**. 아래 절차는 이 조건을 기준으로 진행. 24시간 전원 유지 계획과 실제 절전·앱 실행 설정의 확인은 구분.

## 먼저 알아둘 점

이전 자체는 가능. 다만 개인 노트북도 꺼지거나 잠들면 같은 문제가 발생하므로, 이전만으로 상시 운영이 보장되지는 않음. 현재 로컬 파일 기반 예약 작업은 컴퓨터 전원과 데스크톱 앱 실행이 필요하며, 웹 예약 작업은 PC의 로컬 폴더를 직접 사용할 수 없음. [OpenAI 공식 예약 작업 문서](https://learn.chatgpt.com/docs/automations?surface=app)

아래 절차는 확인된 **Windows → Windows 이전** 기준. 운영체제 변경을 위한 별도 이식은 불필요하지만, 기기별 경로와 Windows 사용자 암호화 저장소(DPAPI)는 다시 설정해야 함.

사용자 확인이 필요한 사항:

1. 실제 준비 상태: 전원·인터넷 연결, 절전 방지, 데스크톱 앱 실행 유지 설정 완료 여부.
2. 회사 업무 자료가 포함된 기사 DB와 발송 이력의 개인 기기 반출이 회사 정책상 가능한지. 불가하면 승인된 기기·호스트로 옮기는 방안 필요.

개인 PC를 종료하거나 시스템이 절전된 동안에도 계속 받아야 한다면 별도 상시 호스트가 필요. 덮개를 닫아도 시스템이 절전되지 않도록 설정하고 통풍을 확보한다면 덮개 닫기 자체는 중단 원인이 아님. 이번에는 사용자가 확인한 상시 운영 Windows PC로 이전하며, 서버 계약·배포·유료 서비스 신청은 수행하지 않음.

## 지금 개인 PC에서 준비할 것

1. 데스크톱 앱 설치 후 현재와 같은 계정으로 로그인. Windows의 로컬 작업 폴더를 사용하는 환경으로 준비. [공식 Windows 설치 안내](https://learn.chatgpt.com/ko-KR/docs/windows/windows-app)
2. 전원과 인터넷을 연결하고 Windows 설정에서 전원 연결 시 시스템 절전을 사용하지 않도록 설정. 화면 꺼짐은 허용 가능. 화면 잠금·로그인 보안을 해제할 필요 없음. 재부팅 후에는 Windows 로그인과 앱 실행 상태를 다시 확인해야 함.
3. 작업용 로컬 폴더 선택. 예: `C:\NewsMonitor`. 사용자 권한으로 쓸 수 있는 경로를 사용하고, 운영 DB를 두 PC가 실시간 파일 동기화하는 방식은 사용하지 않음.
4. 개인 PC의 앱에서 그 폴더를 연 뒤 이 문서와 함께 아래 1단계의 준비 요청을 전달. 같은 계정 로그인만으로 회사 PC의 파일이나 예약 실행 위치가 옮겨지지는 않음.
5. Telegram 봇 토큰·DART 키는 새 PC의 보안 입력 단계에서만 입력하고, Gmail 연결이 요구하는 로그인·동의만 직접 진행. 회사 자료 전달은 허용된 방법을 확인한 뒤 수행.

이 준비 단계에서는 회사 자동화를 계속 유지하고 개인 PC의 예약 뉴스 발송은 아직 활성화하지 않음. 새 PC에 접근할 수 있게 된 뒤 코드 경로·과거 이력 해석·인증·비발송 시험부터 진행.

## 실제 이전 순서

### 1. 노트북 준비 — 회사 자동화는 아직 유지

사용자가 노트북에 데스크톱 앱을 설치·로그인하고 새 작업 폴더를 선택. Windows라면 예를 들어 `C:\NewsMonitor`처럼 사용자 이름에 덜 의존하는 경로 사용 가능. 실제 경로는 선택 후 확정.

노트북에서 이 문서를 열어 다음과 같이 요청:

> 이 문서의 이전 절차를 진행해줘. 기존 회사 PC는 아직 운영 중이므로 노트북의 예약 뉴스 발송은 활성화하지 말고, 런타임·경로·인증·비발송 테스트를 먼저 준비해줘.

회사 PC의 앱 로그인 파일, 전체 `.codex` 폴더, 브라우저 프로필, 런타임 캐시를 개인 노트북으로 복사하지 않음. 기존 작업이 앱에 보이더라도 로컬 DB·스크립트·예약 실행 호스트가 자동으로 이전됐다고 판단하지 않음.

### 2. 코드·설정만 먼저 준비

`outputs/rss-news-monitor`의 코드·테스트·`sources.json`·`PROTOCOL.md`·`COMPANY-WATCHLIST.md`와 `outputs/telegram-forwarder`의 코드·테스트·규칙 템플릿을 선별. 해당 폴더에도 과거 브리프 등 실제 산출물이 있으므로 코드 배포 단계에서 폴더 전체를 무심코 업로드하지 않음.

새 기기의 Python 경로 확인 후 위 세 스크립트의 실행 경로 수정. `PROTOCOL.md`와 예약 프롬프트의 작업 경로도 새 경로 기준으로 정합성 확인. 운영 규칙·소스 범위·기사 선별 기준·명사형 한국어 양식·중복 방지 기준은 변경하지 않음.

현재 시간표는 한국시간 07:00 모닝, 이후 07:40부터 40분 간격, 23:00 마지막 실시간. 이전 문서 일부에 남은 20분 간격 안내를 새 예약 설정으로 사용하지 않음.

### 3. 새 기기에서 인증 — 사용자가 직접 입력할 부분

Windows 노트북에서 새 프로젝트 폴더를 연 상태로, 운영할 Windows 사용자 계정의 PowerShell에서 실행:

```powershell
Set-ExecutionPolicy -Scope Process Bypass
& .\outputs\telegram-forwarder\Setup-Telegram.ps1
```

진행 순서:

1. 기존 Telegram 봇의 토큰을 BotFather에서 확인해 보안 입력창에 입력. 토큰을 채팅에 붙이거나 파일로 전달하지 않음.
2. 기존 봇과의 1:1 대화에 `/start`를 새로 전송.
3. PowerShell로 돌아와 안내에 따라 진행하고 기존 수신 대화방 선택.
4. 연결 시험 메시지 도착 확인. 설정 스크립트는 시험 메시지를 실제 발송하므로 이 메시지는 정상 뉴스와 구분.

기존 봇을 계속 사용하면 새 봇을 만들 필요 없음. 단순 기기 이전만을 이유로 토큰을 폐기·재발급하지 않음. 토큰을 바꾸면 회사 PC도 새 토큰 등록 전까지 발송 불가하므로 필요한 경우 전환 시점과 함께 처리.

OpenDART는 다음 스크립트의 보안 입력창에서 키를 다시 등록:

```powershell
& .\outputs\rss-news-monitor\Setup-Dart.ps1
```

복사 제외 대상은 `.telegram-forwarder`와 `.news-monitor-secrets`의 인증정보 전체. `chat_id`도 이번 이전에서 파일 복사 대신 설정 스크립트로 재탐색. 새 암호화 파일은 반드시 실제 예약 작업을 운영할 Windows 계정에서 생성.

Gmail은 노트북의 연결 도구에서 `hjsnews96@gmail.com` 접근 상태 확인. 로그인 또는 동의 창이 나타나면 사용자가 진행. 기존 뉴스레터 구독과 Gmail 라벨은 메일 계정에 있으므로 PC 이전 때문에 각 사이트를 다시 구독하지 않음. 단, 연결 성공 표시에 그치지 않고 `power news` 라벨 검색과 지정 기관·매체 발신자 검색을 모두 시험.

### 4. 과거 경로를 안전하게 읽을 수 있도록 준비

새 기기의 작업 코드에는 회사 프로젝트 루트 → 새 프로젝트 루트의 **명시적인 과거 경로 해석 기능**이 필요. 현재 일반 경로 처리만으로 서로 다른 루트의 복사본이 완전하게 동작한다고 보장할 수 없으므로, 이 부분을 구현·시험한 뒤 활성화.

구현 시 지켜야 할 조건:

- 원본 DB 백업·영수증·snapshot·발송 본문은 변경 없이 별도 보존.
- 과거 경로는 허용한 회사 프로젝트 루트 하위인 경우에만 동일한 상대경로의 새 파일로 연결.
- 재해석한 최종 경로가 새 프로젝트 루트 밖으로 벗어나면 중단.
- 과거 본문·해시·메시지 ID·URL·run ID·기사 상태는 변경 금지.
- DB의 영수증 경로와 판정의 영수증 경로가 서로 다르게 해석돼 동일한 발송을 다른 결정으로 취급하지 않는지 검증.
- snapshot 복구 모드의 자기 경로 일치 검사와 영수증의 실제 본문 일치 검사까지 통과 필요.
- 과거 complete 영수증 재사용은 실제 전송 없이 멱등 종료, uncertain 영수증은 자동 재전송 차단.

위 경로 이전 기능은 이 문서 작성 시점에 새로 구현된 것이 아님. 이식 단계에서 해결해야 하는 항목.

### 5. 비발송 시험 완료 후 회사 쪽을 정지하고 최종 백업

전환 시각을 정한 다음 아래 순서 준수:

1. 회사 앱의 예약 관리에서 기존 뉴스 자동화를 일시정지. 현재 실행이 있다면 성공 발송과 기록 처리가 마무리됐는지 확인 후 다음 단계로 이동. 이 문서 작성 과정에서는 정지하지 않았음.
2. 수집·발송·ACK 프로세스가 더 이상 DB와 이력을 쓰지 않는지 확인.
3. 이미 성공 발송했으나 DB에 미반영된 항목은 기존 snapshot·성공 영수증에 근거해 ACK 복구. 모호한 발송은 보류하고 임의 재전송하지 않음.
4. SQLite Backup API 등 SQLite가 지원하는 일관된 백업 방법으로 **새 이름의 DB 백업** 생성. 운영 DB를 덮어쓰지 않음. DB가 쓰이는 중 `.db` 파일 하나만 탐색기로 복사하지 않음. [SQLite 공식 백업 설명](https://www.sqlite.org/backup.html)
5. 같은 전환 시점의 `work/runs` 이력과 필요한 본문 파일, `work/telegram-outbox`의 과거 이력을 함께 보존. 영수증만 복사하거나 DB만 복사하는 방식 금지. 본문 해시에 영향을 주므로 줄바꿈·인코딩 자동 변환도 금지.
6. 백업 DB에 읽기 전용 무결성 검사 수행. 기사 상태별 수, `delivery_history`, `decision_history`, `newsletter_messages`, `newsletter_message_articles`의 행 수와 발송 본문 해시 집계 기록. 원본 자료를 채팅에 나열할 필요 없음.
7. 회사 정책상 허용된 경로로 노트북에 전달하고 파일 해시·DB 집계 재대조. 개인 메일·기사 데이터가 들어 있는 `work` 전체를 공개 저장소·공개 파일 공유에 올리지 않음.

Gmail 원문 임시파일 등은 발송 증거·미처리 보존에 정말 필요한지 개별 확인 후 허용된 것만 이전. 메일 처리 ID와 기사 연결 관계는 DB에서 유지하여 같은 메일의 불필요한 재처리 방지.

### 6. 노트북의 최종 검증

새 예약 발송을 켜기 전 확인 항목:

- 모든 수집·판정·메일 큐·발송 중복 방지 테스트 통과.
- 원본과 백업의 무결성·기사 상태별 수·발송/결정/메일 기록 수 일치.
- 전 기간 발송 이력에서 실제 본문·해시·메시지 ID 보존.
- 이미 보낸 대표 기사로 전송 사전 검사를 수행했을 때 중복 차단.
- 수집은 한 회차에서 한 번만 수행하고, 전체 색인과 미처리 대기열 접근 가능.
- Gmail 라벨/발신자 두 검색 모두 정상. 기사 추출과 처리 ID 저장의 연결 유지.
- Telegram의 일반 연결 시험뿐 아니라 실제 예약 환경에서도 발송 스크립트 접근 가능. 허용 규칙은 새 경로의 고정 스크립트에만 적용하고 앱을 재시작해 적용 확인.
- 뉴스 형식 검사에서 `valid=true`뿐 아니라 `novelty_checked=true` 확인. `-ValidateOnly`를 붙였다는 사실만으로 중복 검사 완료라고 판단하지 않음.
- 성공 영수증에 실제 메시지 ID 저장 후 해당 고유 run의 `Ack-Collector.ps1 -DecisionFile`을 통한 기록 확인.

`Run-Collector.ps1 -Mode status`는 이름과 달리 내부적으로 스키마 확인과 commit 코드가 있으므로, 최종 백업의 순수 읽기 무결성 검사 대용으로 사용하지 않음.

### 7. 한 기기만 예약 발송 활성화

회사 자동화의 정지 상태 확인 후 노트북의 현재 작업에 예약을 연결. 앱의 예약 관리 기능을 사용하고 설정 파일을 수동 전체 복사하지 않음. 처음에는 기존 작업이 이미 동기화되어 있는지 확인해 중복 예약 생성 방지.

한국시간 07:00 모닝 및 40분 간격 실시간, 23:00 이후~07:00 미만 미실행, 새 실패·의미 있는 뉴스만 알림 원칙 유지. 평소 개별 기사 양식 사용, 별도 복구 브리프 양식 재도입 금지.

첫 수동 회차와 다음 실제 예약 회차를 각각 확인한 뒤 이전 완료 판정. 수동 테스트 한 번 성공만으로 무인 예약까지 정상이라고 보고하지 않음.

전원 연결 상태의 절전·최대절전·덮개 닫기 동작을 사용자가 원하는 운영 방식에 맞게 설정. 화면 꺼짐과 시스템 절전은 구분. 덮개를 닫고 운영한다면 통풍이 확보된 환경 유지. 운영체제 업데이트·인터넷 장애·앱 종료로 인한 중단 가능성은 남으므로, 수집 시각·전송 영수증·새 실패 감시도 유지.

### 8. 문제 발생 시 되돌리기

노트북을 먼저 정지한 뒤 회사 PC 재개 여부 결정. 노트북에서 이미 성공 발송한 메시지가 있다면 **그 최신 성공 이력과 상태를 보존·합친 뒤** 회사 쪽을 재개. 옛 회사 DB만 바로 켜면 노트북에서 보낸 기사가 다시 전송될 수 있음.

원본 DB와 과거 기록은 전환 검증 전 삭제하지 않음. 복구 시에도 두 기기를 동시에 켜서 중복 발송시키지 않음.

## 역할 구분

Windows·24시간 운영 계획은 확인 완료. 사용자가 직접 해야 하는 일은 개인 PC의 전원·절전 설정과 앱 로그인, Telegram 토큰·DART 키 보안 입력, 필요한 Gmail 재동의, 회사 자료의 반출 가능 여부 확인. 그 외 코드 경로 조정·안전한 이력 경로 처리·테스트·검증·예약 설정 대조는 새 기기 접근이 가능한 상태에서 이어서 수행 가능.

현재는 이전 계획과 장애 지점을 정리한 상태이며, 개인 노트북으로 실제 워크플로우가 이전되거나 회사 자동화가 꺼진 상태가 아님.
